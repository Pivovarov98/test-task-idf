# Bank Transactions API

Месячный лимит по умолчанию — 1000 USD отдельно для каждой категории счёта;
бизнес-календарь использует московское время (UTC+3).
Клиентский API установки лимита, регистрация счетов и блокировки описаны в
[LIMIT_CREATION.md](LIMIT_CREATION.md).
Резервирование расходов, завершение операций и управляемая заглушка банка описаны в
[OPERATIONS.md](OPERATIONS.md).

Сервис приёма банковских транзакций. Проверяет входные данные, присваивает UUID и время
получения в UTC, сохраняет транзакцию в PostgreSQL и возвращает HTTP `201`.
Клиентский API устанавливает лимиты, сохраняя историю изменений. API доступны без авторизации.

## Курсы валют и расчёт USD

Источник — Open Exchange Rates. В бесплатном тарифе используется база USD; один запрос
`/historical/YYYY-MM-DD.json` возвращает дневные значения всех доступных валют.
App ID передаётся только через окружение, не сохраняется в репозитории и не выводится в лог:

```powershell
$env:OPEN_EXCHANGE_RATES_APP_ID = '<ваш App ID>'
$env:DB_URL = 'jdbc:postgresql://localhost:15432/test_task_idf'
./mvnw.cmd spring-boot:run
```

В настройках Run Configuration IDE добавьте эти переменные в Environment variables.
Без App ID приложение принимает транзакции, использует сохранённые курсы и оставляет
нерассчитанные операции в `PENDING`; внешние запросы не выполняются.
`EXCHANGE_RATES_ENABLED=false` отключает фоновый обработчик и расписание.

Open Exchange Rates предоставляет последние опубликованные значения за день UTC,
а не биржевые OHLC-свечи. По согласованному правилу проекта завершённые дневные значения
считаются аналогом `close`. Отдельного поля `previous_close` у источника нет.
Документация источника: https://docs.openexchangerates.org/reference/historical-json.

В 09:00 МСК ежедневно планируется загрузка предыдущего завершённого дня UTC. При старте
приложение также проверяет его наличие, восстанавливая пропущенное обновление.
Дата расхода определяется из `datetime` по UTC; месячный календарь лимитов остаётся московским.
Для прошедшего рабочего дня нужен снимок за этот день. Для текущего или будущего дня используется
последний завершённый рабочий день UTC, поскольку сегодняшний курс ещё не является закрытием.
Суббота и воскресенье пропускаются. Дата выбора курса фиксируется при получении операции;
её последующее завершение не меняет дату и сумму USD. Особенности праздников источника
описаны в OPERATIONS.md.
Если источник вернул более раннюю дату публикации, она сохраняется как дата предыдущего
закрытия (`rate_date`), отдельно от запрошенной даты (`requested_date`). Выходной не определяется
по отсутствию HTTP-ответа: источник может публиковать снимки и в выходные.

Приём транзакций не вызывает внешний API. Транзакция и задание на получение недостающего
снимка сохраняются в PostgreSQL; HTTP `201` подтверждает сохранение исходной операции.
Ответ дополнен полями:

| Поле | Значение |
| --- | --- |
| `amount_usd` | Сумма в USD либо null, пока расчёт не завершён |
| `conversion_status` | `COMPLETED`, `PENDING` или `UNSUPPORTED_CURRENCY` |
| `exchange_rate_id` | Ссылка на сохранённый курс; null для USD или незавершённого расчёта |

Для USD расчёт завершается сразу с курсом 1. Для других валют сначала используется БД.
Фоновый обработчик каждые 10 секунд обрабатывает ожидающие операции и загружает максимум
одно задание за проход. Даты заданий уникальны; атомарная аренда строки на 60 секунд
предотвращает одновременную загрузку одной даты несколькими экземплярами приложения.
HTTP-вызовы выполняются вне транзакции БД. Все валюты из ответа сохраняются одной
короткой транзакцией. Очередь и состояния операций переживают перезапуск; истёкшая аренда
позволяет забрать задание после аварийного завершения процесса.

Расчёт: `amount_usd = sum / units_per_usd`, `BigDecimal`, округление до двух знаков `HALF_UP`.
Курс хранится в PostgreSQL как NUMERIC без ограничения масштаба; его исходная точность сохраняется.
Завершённая операция автоматически не пересчитывается. Отсутствие валюты в корректном полном
снимке даёт `UNSUPPORTED_CURRENCY`; отсутствие снимка или сбой API оставляет `PENDING`.
По правилам резервирования из пункта 4 при отсутствии нужного снимка используется последний
предыдущий сохранённый курс. Если подходящих данных совсем нет, операция остаётся PENDING.

Таймаут подключения — 2 секунды, одной попытки — 5 секунд; при транспортном сбое или `5xx`
выполняются максимум две дополнительные попытки с задержкой. Затем задание откладывается
с увеличением интервала до одного часа. `429` не повторяется немедленно: учитывается
`Retry-After` (секунды или HTTP-дата), без заголовка ожидание — час. Остальные HTTP-ошибки
блокируют дальнейшие внешние запросы до перезапуска после исправления конфигурации.
Причина записывается безопасным кодом в `last_error`; URL с App ID и тело ошибки не логируются.
Сбой источника не отменяет сохранённые транзакции. Если БД недоступна при приёме,
успешное сохранение невозможно, поэтому API возвращает ошибку ProblemDetail.

Таблицы миграции V5: `exchange_rate_snapshots`, `exchange_rates`, `exchange_rate_jobs`;
в `transactions` добавлены сумма USD, статус, ссылка на курс и время повторной обработки.

## Установка лимита

`POST http://localhost:8080/api/v1/client/limits`:

```json
{
  "account": "0000000123",
  "expense_category": "product",
  "amount": 1500.00
}
```

Ответ `201` содержит `id`, `account`, `expense_category`, `amount`, `currency: USD`
и `established_at` с часовым смещением `+03:00`. Дату и валюту назначает сервер;
передача этих или неизвестных полей возвращает `400`.

Новый счёт регистрируется автоматически; пока лимит не установлен, действует 1000 USD
отдельно для `product` и `service`. Лимит может быть нулевым. Каждая установка создаёт
новую запись, существующие записи обновлять нельзя.

Повтор того же запроса вернёт `409` с `code: limit_amount_unchanged`, включая попытку
установить дефолтные 1000 USD. Если другой запрос для того же счёта и категории ещё
выполняется, ответ — `409` с `code: limit_request_in_progress`. Другие категории и счета
обрабатываются параллельно. Ошибки используют ProblemDetail (RFC 9457).

Для проверки в Swagger сначала установите 1500, затем повторите запрос (ожидается 409),
затем установите 0 (ожидается 201). В категории `service` останется дефолтный лимит 1000 USD.

## Получение всех лимитов счёта

```http
GET http://localhost:8080/api/v1/client/accounts/0000000123/limits?page=0&size=20
```

Ответ содержит `content`, `page`, `size`, `total_elements`, `total_pages`.
Элементы `content` имеют поля `id`, `account`, `expense_category`, `amount`, `currency`, `established_at`.
Возвращаются все пользовательские установки, включая нулевые, и дефолтные лимиты 1000 USD.
Для дефолта `id` равен `null`, а дата — начало месяца по Москве (UTC+03:00).
Начальные дефолты включаются для обеих категорий в месяце регистрации счёта; последующие —
только за месяцы с операциями, до которых ещё не действовал пользовательский лимит соответствующей категории.
Установленный лимит переносится на следующие месяцы. Чтение не создаёт записи в БД.

Сортировка: `established_at DESC`, затем `revision DESC`, затем `expense_category ASC`;
техническая ревизия в ответ не включается. Страницы нумеруются с нуля, размер по умолчанию 20,
допустимый диапазон — 1–100. Страница за пределами истории возвращается с пустым `content`.
Неверный счёт или параметры страницы — `400 ProblemDetail`, неизвестный счёт — `404` без регистрации.
Общее количество и содержимое страницы читаются в одной транзакции `REPEATABLE_READ`.
SQL использует `JOIN` с агрегированными подзапросами, `MIN` и `GROUP BY`.

## Получение превышенных транзакций

```http
GET http://localhost:8080/api/v1/client/accounts/0000000123/transactions/limit-exceeded?page=0&size=20
```

Возвращаются только операции `SUCCEEDED` с `limit_check_status=COMPLETED` и `limit_exceeded=true`.
Неуспешные, ожидающие расчёта и находящиеся в `TIMED_OUT` операции исключаются, даже если
их технический флаг равен `true`. Позднее подтверждение успеха может добавить операцию в список.

Каждый элемент `content` содержит ровно девять полей: `account_from`, `account_to`,
`currency_shortname`, `sum`, `expense_category`, `datetime`, `limit_sum`, `limit_datetime`,
`limit_currency_shortname`. `sum` и валюта сохраняют исходные значения транзакции;
`limit_sum` — сумма лимита в USD, закреплённая при резервировании. Дата пользовательского
лимита берётся из связанной исторической записи; дата дефолтного — начало месяца создания
операции по Москве. Даты в ответе представлены со смещением `+03:00`.
Чтение не пересчитывает USD, флаги или применённые лимиты и не обращается к внешнему API.

Сортировка: `datetime DESC`, затем `operation_sequence DESC`. Фильтров категории и периода нет.
Оболочка страницы: `content`, `page`, `size`, `total_elements`, `total_pages`.
Параметры страницы и ошибки совпадают с получением лимитов: страницы с нуля, размер 20
по умолчанию и максимум 100, `400` для неверного запроса, `404` для неизвестного счёта.
Известный счёт без превышений получает `200` с пустым `content` и нулевым количеством страниц.
Подсчёт и выборка выполняются в одной транзакции `REPEATABLE_READ`; между отдельными
запросами страниц новые завершения операций могут сдвинуть выдачу.

Исторический лимит при резервировании выбирается через `JOIN` с подзапросом,
`MAX(established_at)` и `GROUP BY`, а при чтении превышений используется сохранённый `applied_limit_id`.
Миграция V7 добавляет частичный индекс для завершённых успешных превышений.

## Локальный запуск

Нужны JDK 21 и Docker с Docker Compose. Maven устанавливать отдельно не нужно — есть Maven Wrapper.
Из корня проекта запустите БД, затем приложение:

```powershell
docker compose up -d --wait
./mvnw.cmd spring-boot:run
```

В Linux/macOS используйте `./mvnw` вместо `./mvnw.cmd`.
Flyway автоматически создаёт таблицу и применяет миграции при старте приложения.
Приложение слушает порт `8080`; Compose публикует PostgreSQL на `127.0.0.1:5432`.
Если `5432` занят локальным PostgreSQL, используйте другой порт, например `15432`:

```powershell
$env:DB_PORT = '15432'
$env:DB_URL = 'jdbc:postgresql://localhost:15432/test_task_idf'
docker compose up -d --wait
./mvnw.cmd spring-boot:run
```

В IDE для этого варианта: host `localhost`, port `15432`, database `test_task_idf`,
user и password `test_task_idf`. При смене порта Docker volume с данными сохраняется.
Остановить БД можно командой `docker compose stop`; данные сохраняются в Docker volume.

Для запуска собранного приложения:

```powershell
./mvnw.cmd package -DskipTests
java -jar target/test-task-idf-0.0.1-SNAPSHOT.jar
```

## Приём транзакции

`POST /api/v1/bank/transactions`, `Content-Type: application/json`.
Все шесть полей обязательны:

| Поле | Тип | Ограничения |
| --- | --- | --- |
| `account_from` | string | Ровно 10 цифр; ведущие нули сохраняются |
| `account_to` | string | Ровно 10 цифр |
| `currency_shortname` | string | ISO 4217, поддерживаемый Java; регистр важен, например `KZT` |
| `sum` | number | Больше нуля; до 17 цифр целой части и до 2 знаков дробной части |
| `expense_category` | string | `product` или `service` |
| `datetime` | string | ISO 8601 с часовым смещением, например `+06:00` или `Z` |

Пример тела запроса:

```json
{
  "account_from": "0000000321",
  "account_to": "9999999999",
  "currency_shortname": "KZT",
  "sum": 10000.45,
  "expense_category": "product",
  "datetime": "2022-01-30T00:00:00+06:00"
}
```

Пример вызова в PowerShell:

```powershell
$body = @{
    account_from = '0000000321'
    account_to = '9999999999'
    currency_shortname = 'KZT'
    sum = 10000.45
    expense_category = 'product'
    datetime = '2022-01-30T00:00:00+06:00'
} | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri 'http://localhost:8080/api/v1/bank/transactions' `
    -ContentType 'application/json' -Body $body
```

Успешный ответ: HTTP `201`, `application/json`. UUID и время получения ниже приведены для примера:

```json
{
  "id": "a0187ed2-b40a-4cde-86e2-68972c69dd10",
  "account_from": "0000000321",
  "account_to": "9999999999",
  "currency_shortname": "KZT",
  "sum": 10000.45,
  "expense_category": "product",
  "datetime": "2022-01-30T00:00:00+06:00",
  "received_at": "2026-10-07T12:00:00Z"
}
```

Каждый запрос создаёт новую запись: API не поддерживает идемпотентность и дедупликацию.
`datetime` обозначает время операции, `received_at` — время получения сервером.
PostgreSQL хранит временные поля как `TIMESTAMP WITH TIME ZONE`: сохраняется момент времени,
но исходное смещение не хранится; точность БД — микросекунды.

### Ошибки

Ошибки возвращаются в формате `application/problem+json`.

| Статус | Причина |
| --- | --- |
| `400` | Некорректный JSON, формат даты, значения полей или нарушение ограничений |
| `405` | Неподдерживаемый HTTP-метод |
| `415` | Неподдерживаемый тип содержимого запроса |
| `503` | Ошибка сохранения транзакции |
| `500` | Непредвиденная серверная ошибка |

Пример ошибки валидации (текст сообщения зависит от валидатора):

```json
{
  "type": "about:blank",
  "title": "Bad Request",
  "status": 400,
  "detail": "Request validation failed",
  "instance": "/api/v1/bank/transactions",
  "errors": {
    "account_from": "must match \"[0-9]{10}\""
  }
}
```

Объект `errors` присутствует при Bean Validation и использует входные имена полей в snake_case.
При ошибке разбора JSON, ошибке БД или непредвиденном исключении этого объекта нет.

## Устройство проекта

- `controller` — HTTP API и обработка ошибок в формате ProblemDetail.
- `dto` — контракт запроса и ответа, валидация и Swagger-схемы.
- `service` — генерация UUID, время из Clock, транзакционная граница и MapStruct-маппер.
- `repository` — вставка через JdbcTemplate с параметрами.
- `accounts` в БД — реестр счетов; `transactions.account_from` и `expense_limits.account`
  ссылаются на него. `account_to` хранится как счёт контрагента без обязательной регистрации.
- `model` — неизменяемая модель с доменными ограничениями.
- `config` — Clock, валидатор валюты и метаданные OpenAPI.
- `util` — преобразование категорий и имён полей.
- `src/main/resources/db/migration` — версионированные SQL-миграции Flyway.

Сохранение и построение ответа выполняются в одной транзакции. Runtime-исключение,
включая ошибку маппинга ответа после INSERT, приводит к rollback.
Регистрация счёта выполняется отдельной транзакцией и сохраняется при отклонении установки лимита.

## Тестирование и проверки

Полный прогон требует запущенного Docker:

На Linux/macOS: `./mvnw verify` (JDK 21+, Docker; ручной запуск БД не нужен).
`JanuaryScenarioApiTests` воспроизводит «1 случай» через RestClient и реальный HTTP-порт
(`@SpringBootTest(RANDOM_PORT)`). PostgreSQL 17 запускается в Testcontainers, внешний API
курсов заменён WireMock на случайном порту; тест проверяет обращение фонового загрузчика к нему.
Управляемый Clock задаёт январские даты без зависимости от текущего времени.
Исходный лимит — дефолтные 1000 USD с 1 января. Через HTTP он повышается до 2000 USD 10 января, отправляются
все шесть расходов (500, 600, 100, 700, 100, 100 USD) и подтверждения банка.
Итоговый GET проверяет ровно два превышения — 3 января и вторую операцию 13 января —
со всеми исходными полями и историческими датой, суммой и валютой лимита.
Операция, доводящая расход ровно до 2000 USD, превышением не считается.

```powershell
./mvnw.cmd verify
```

Testcontainers поднимает отдельную PostgreSQL 17. Spring Boot подключает её через
`@ServiceConnection` и управляет жизненным циклом контейнера. Локальная БД для тестов не нужна.
API-тесты проверяют запросы, валидацию, сохранение, OpenAPI и доступность Swagger UI.
Интеграционные тесты сервиса проверяют commit и rollback, тесты миграций — ограничения БД.
Клиентские запросы проверяются на январском и февральском примерах задания: исторические
лимиты, дефолты, нулевые суммы лимитов, точный формат ответа и исключение неуспешных операций.
Проверяются пагинация, сортировка одинаковых дат, изоляция счетов, ошибки валидации и БД,
а также согласованность количества и содержимого страницы при параллельных изменениях.
Для жизненного цикла операций проверяются резервирование и возврат суммы, исторические лимиты,
нулевой лимит, границы месяца по Москве, отложенная конвертация и неизменность суммы в USD.
Параллельные запросы проверяют блокировки на PostgreSQL, включая гонку таймаута с уведомлением об успехе.
Управляемый Clock позволяет проверить три часа ошибок, сброс таймера при ответе PROCESSING
и позднее завершение без ожидания в реальном времени. Проверяются также ProblemDetail,
идемпотентность уведомлений, ответы банковской заглушки и восстановление таймера после перезапуска.
Для конвертации проверяются точность курсов, округление HALF_UP, дата UTC, кэш и previous_close,
состояния PENDING и UNSUPPORTED_CURRENCY, аренда задания и атомарность сохранения снимка.
Отдельный тест закрывает и заново запускает Spring-приложение на той же тестовой БД,
проверяя восстановление незавершённой операции. Клиентские тесты имитируют таймаут,
сетевой разрыв, некорректный JSON, 5xx, 429 и ошибку App ID. Реальный внешний API не вызывается;
профиль test отключает расписание и очищает App ID, поэтому квота провайдера не расходуется.

Unit-тесты можно выполнить без Docker:

```powershell
./mvnw.cmd test
```

`verify` также выполняет архитектурные проверки ArchUnit, Checkstyle и SpotBugs.
Отчёт покрытия JaCoCo: `target/site/jacoco/index.html`.
Maven автоматически активирует профиль `test` из `src/test/resources/application-test.properties`.
Подключение к БД задаёт `@ServiceConnection`; резервный URL намеренно недоступен, чтобы при
отсутствии контейнерной конфигурации тест не подключился к локальной рабочей БД.
Параллельное выполнение JUnit отключено, поскольку интеграционные тесты используют общий Spring-контекст.

Surefire выполняет unit-тесты и ArchUnit в фазе `test`. Failsafe выполняет классы
`*IntegrationTests`, `*ApiTests`, `*MigrationTests` и `TestTaskIdfApplicationTests` в фазе
`integration-test` и проверяет результаты в `verify`. Для новых интеграционных тестов используйте
суффикс `IntegrationTests` и импорт `PostgresTestConfiguration`.
Результаты: `target/surefire-reports` и `target/failsafe-reports`.

### Test-stage в CI

GitHub Actions (`.github/workflows/ci.yml`) запускается на push, pull request и вручную:

1. `build` собирает JAR на JDK 21 и сохраняет артефакт `application-jar`.
2. `test` (Test stage) после успешной сборки проверяет доступность Docker и запускает
   `./mvnw --batch-mode --no-transfer-progress clean verify`.
3. Testcontainers самостоятельно создаёт PostgreSQL на динамическом порту; отдельный
   PostgreSQL service и секреты подключения к БД в CI не нужны.
4. Ошибка тестов, ArchUnit, Checkstyle или SpotBugs завершает test-stage с ошибкой.
   Отчёты Surefire, Failsafe, Checkstyle, SpotBugs и JaCoCo сохраняются в артефакт
   `test-and-quality-reports` на 7 дней даже при неуспешном прогоне.

Анализ SonarQube включается при настройке `SONAR_HOST_URL`, `SONAR_PROJECT_KEY` и секрета
`SONAR_TOKEN`; для SonarCloud также нужен `SONAR_ORGANIZATION`.

## Проектный Agent Skill

[`.agents/skills/idf-limit-tests/SKILL.md`](.agents/skills/idf-limit-tests/SKILL.md)
помогает добавлять и проверять тесты месячных лимитов: исторические значения,
резервирование, границы сумм и HTTP-выдачу превышений. Внутри — ссылки на реальные
тесты и сервисы, использование `PostgresTestConfiguration` и тестового Clock,
контракты HTTP, WireMock и команды Surefire/Failsafe.

Файл использует [открытый формат Agent Skills](https://agentskills.io/specification):
YAML-заголовок `name`/`description` и инструкции Markdown. Каталог
`.agents/skills/` поддерживается [обнаружением скиллов Codex](https://learn.chatgpt.com/docs/build-skills).
Скилл хранится в репозитории; устанавливать его в домашний каталог не нужно.
В Codex CLI можно проверить наличие через `/skills` и вызвать явно:

```text
$idf-limit-tests Проверь покрытие границы месячного лимита и предложи недостающий тест.
```

Для проверки автоматического выбора запусти из корня репозитория (нужен авторизованный Codex CLI):

```sh
codex exec --ephemeral --sandbox read-only --json \
  'Проверь покрытие тестами месячных лимитов в этом проекте. Найди проверку точного равенства расхода лимиту и исторического лимита в январском HTTP-сценарии. Используй подходящий проектный скилл, если он доступен. Ничего не меняй и не запускай Maven. Укажи применённый скилл и прочитанные файлы.'
```

В событиях должны быть выбор `idf-limit-tests`, чтение его `SKILL.md` и анализ
реальных тестов с учётом инструкций. Одного упоминания имени в ответе недостаточно.
Если новый скилл не появился в текущем клиенте, перезапусти Codex из корня проекта.
Для Claude Code можно использовать тот же файл через симлинк `.claude/skills` →
`../.agents/skills` (из каталога `.claude`); отдельную копию инструкций поддерживать не нужно.

Проверено 09.10.2026 на `codex-cli 0.154.0-alpha.6.2` отдельным запуском
`codex exec --ephemeral --sandbox read-only --json`: имя и путь скилла в запрос не передавались.
Агент сам объявил «Применю проектный скилл `idf-limit-tests`», выполнил
`cat .agents/skills/idf-limit-tests/SKILL.md` (exit 0), прочитал проектные тесты и
нашёл `exactLimitIsNotExceededButNextPositiveAmountIs` и проверки исторических лимитов
в `JanuaryScenarioApiTests`. По инструкции не дублировать январский сценарий он предложил
отдельную HTTP-проверку переноса пользовательского лимита со сбросом расхода на московской
границе месяца и команду Failsafe `verify`. Это была проверка применения скилла в режиме
анализа: предложенный тест не создавался, Maven в этом запуске не выполнялся.
YAML-заголовок проверен валидатором `skill-creator` (`Skill is valid!`),
все 14 относительных ссылок внутри скилла ведут к существующим файлам.
