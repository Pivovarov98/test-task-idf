# Резервирование и завершение банковских операций

Приём операции: `POST /api/v1/bank/transactions`, прежние поля JSON сохраняются.
В ответ добавляются `operation_status`, `completed_at`, `limit_exceeded`,
`limit_check_status`, `reserved_usd` и `reservation_active`.

Новая операция имеет статус PROCESSING. Пока она не завершилась, флаг false,
проверка PENDING; резерв при этом уже занимает часть месячного лимита.
Сумма USD фиксируется при расчёте и не меняется при завершении операции.
Дата курса (`conversion_rate_date`) фиксируется при приёме: дата создания по UTC,
но не позднее предыдущего завершённого дня UTC относительно received_at.
При отсутствии нужного снимка используется последний сохранённый предыдущий курс;
его идентификатор сохраняется. Более новый курс после этого не заменяет использованный.
Если ни одного подходящего курса нет, операция сохраняется и ожидает расчёта.
Суббота и воскресенье пропускаются при выборе даты курса. Для праздников используется
предыдущее закрытие, если источник сообщает более раннюю дату публикации или нужного
снимка ещё нет. Собственного биржевого календаря праздников у OER нет: его дневные
значения используются как согласованный аналог закрытия, без гарантии биржевого OHLC.

Месяц расходов — календарный месяц в UTC+03:00 (Москва), по datetime.
Резервы и успешные расходы учитываются отдельно для account_from и категории product/service.
Лимит выбирается на момент создания, по умолчанию 1000 USD. Смена лимита не обнуляет расходы.
При резервировании сохраняются два результата: превышение с учётом новой суммы и
наличие превышения до этой операции. Равенство лимиту не является превышением.

При SUCCEEDED резерв становится расходом без повторного списания, флаг принимает
первый сохранённый результат. При FAILED резерв освобождается ровно на reserved_usd,
а флаг true остаётся только если превышение уже существовало до этой операции.
Для нулевого лимита положительная сумма USD создаёт превышение; нулевая сумма USD
после округления сама по себе превышение не создаёт.
При завершении до готовности USD успех ожидает расчёта, а неуспех не создаёт резерв.
Операции без известной суммы USD задерживают резервирование последующих операций месяца.
Если операция создана в одном месяце и завершена в другом, расход остаётся в исходном месяце.

История проверок не пересчитывается после освобождения других резервов или установки лимита.
Создание задним числом перед уже рассчитанным резервом этого счёта/категории/месяца
отклоняется с 409. При одинаковом datetime порядок задаётся operation_sequence.
Создание, резервирование, завершение и освобождение используют одну транзакционную
блокировку PostgreSQL по счёту и категории. Другие счета и категории независимы.
Конкурирующие операции ждут завершения друг друга; установка лимита по-прежнему
использует неблокирующую попытку получить эту же блокировку.

## Нотификация банка

`POST http://localhost:8080/api/v1/bank/notifications`:

```json
{
  "transaction_id": "UUID из ответа при создании",
  "status": "SUCCEEDED",
  "completed_at": "2026-10-09T12:00:00+03:00"
}
```

Вместо SUCCEEDED можно передать FAILED. Время завершения не может предшествовать datetime.
Ответ 200 содержит актуальное состояние. Одинаковая повторная нотификация идемпотентна,
конфликтующие окончательные статусы дают 409, неизвестная операция — 404.
Ошибки — ProblemDetail, входящие тела проходят Bean Validation.

## Заглушка для Postman

Настроить следующий ответ банка:
`PUT http://localhost:8080/api/v1/bank/stub/transactions/{id}`

```json
{"status":"ERROR"}
```

Допустимы PROCESSING, SUCCEEDED, FAILED, ERROR. Это настройка заглушки, а не немедленная
нотификация: ответ будет использован при следующем переопросе. Реального HTTP API банка нет.
Для просмотра состояния:
`GET http://localhost:8080/api/v1/bank/transactions/{id}/status`.
Этот диагностический банковский endpoint не является клиентским списком из пункта 6.

Переопрос по умолчанию каждые 15 минут. Первый ERROR начинает отсчёт недоступности;
последующие ошибки не сдвигают его. PROCESSING очищает отсчёт. После трёх часов
непрерывных ошибок операция становится TIMED_OUT, резерв освобождается один раз.
Флаг при таймауте выставляется по правилу FAILED. Без ошибки таймер не начинается:
банк может сколько угодно подтверждать PROCESSING.
Рабочий обработчик проверяет очередь каждые 10 секунд; завершение по таймауту происходит
на первом переопросе после истечения заданного интервала, а не обязательно в точную секунду.

Поздний SUCCEEDED после TIMED_OUT разрешён: расход восстанавливается на прежнюю сумму
в прежнем месяце, флаг берётся из первоначального резервирования. Остаток может стать
отрицательным. Поздний FAILED не освобождает уже возвращённую сумму повторно.
Повторный SUCCEEDED после успешной финализации повторно расход не увеличивает.
Состояние заглушки, таймер и резервы хранятся в БД и переживают перезапуск.

Для быстрого локального сценария задайте до запуска приложения:

```powershell
$env:BANK_UNAVAILABILITY_TIMEOUT = 'PT3M'
$env:BANK_POLL_INTERVAL = 'PT15S'
$env:BANK_WORKER_DELAY_MS = '1000'
```

Создайте операцию, настройте ERROR и наблюдайте состояние. PROCESSING сбросит отсчёт;
повторный ERROR начнёт новый. После TIMED_OUT отправьте нотификацию SUCCEEDED.
Для отключения обработчика: `BANK_WORKER_ENABLED=false`.

Миграция V6 добавляет состояние операции и резервирования. Данные до этой миграции
получают PROCESSING и будут обработаны по тем же правилам. Пункт 6 не реализован.
